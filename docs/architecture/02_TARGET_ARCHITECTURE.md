## 2. Audit Findings: Current Architectural Deficiencies

1. **Catastrophic CPU Latency (51.10 s/page)**: Dominated by 15.8 sequential unbatched PaddleOCR calls on CPU taking 49.85 s (97.56% of runtime) (`01_AUDIT_FACTS.md:102-117`, `PROFILE_REPORT.md:15, 24`).
2. **Production Format Blindness**: `/predict` lacks format detection and hardcodes `format_original`, causing vertical clipping on Format V2 cover sheets unless YOLO hits (`01_AUDIT_FACTS.md:134-140`, `ocr/pipeline.py:119`).
3. **Silent Subject Code Defaulting**: Missing or unparseable subject codes default silently to `"CT10718"`, concealing extraction failures (`01_AUDIT_FACTS.md:126, 178`, `ocr/postprocessing/cleaning.py:246`).
4. **Hardcoded Data Constants in Code**: Roll prefix `"0801CA25"`, max marks `70`, and layout crop boxes are hardcoded across Python modules instead of external declarative configuration (`01_AUDIT_FACTS.md:173-195`).
5. **False Safety Net in CI**: The 95.21% regression test runs only on static CSV text, giving zero protection against vision, detection, or cropping regressions (`01_AUDIT_FACTS.md:215, 221`, `evaluation/benchmark.py:161`).
6. **Dead Subject Code Fallback**: `ocr/detection/fallbacks.py:18` defines a fallback for subject code, but `ocr/pipeline.py:141` sets crop to `None` on YOLO miss without calling it (`01_AUDIT_FACTS.md:126, 281`).
7. **Monolithic Responsibilities**: `OCREngine.process_image` mixes 9 distinct responsibilities from raw decoding to morphology, multi-engine OCR, and response serialisation (`01_AUDIT_FACTS.md:158-170`).
8. **Tuned-on-Test Evaluation**: Benchmark A (146) and B (145) have no train/val/test splits; regexes and fallback bounds were iteratively tuned on the exact test sets (`01_AUDIT_FACTS.md:219-223`).

## 6. Reader Plan: Comb Strips, Handwritten Codes & Total Marks

### 6.1 Comb Strip Enrollment Reader (Primary Architecture)
- **Evolution from Sliced CNN to Strip-Based ONNX**:
  - Spike 1 (`experiments/spike_comb_cnn/SPIKE_REPORT.md`) and Spike 2 (`experiments/spike_comb_cnn/SPIKE2_REPORT.md`) evaluated single-cell segmentation and 10-class CNN classification. Cell slicing suffered from boundary shifts, slant clipping, and lower accuracy (70.44% tail-4 exact in Spike 3).
  - Spike 3 (`experiments/spike3_enrolment/SPIKE3_REPORT.md`) established that **strip-based recognition** using red-channel dropout on the unified 12-cell comb box achieved **94.09% tail-4 exact match** (191/203 tune sheets) with `0801CA25` prefix enforcement, decisively outperforming sliced CNN classification.
  - Spike 4 (`experiments/spike4_strip_reader/SPIKE4_REPORT.md`) benchmarked `PP-OCRv6_medium_rec_onnx` via ONNX Runtime: CPU inference was **47.7 ms** with tail-4 exact match of 94.09% (191/203) across all 5 folds. Confidence routing accepted 162/203 sheets at $\tau \ge 0.90$ with **98.77% accuracy**.
  - **Decision**: Sliced CNN is **NOT** the primary reader. The production primary reader is **strip-based ONNX recognition-only** (`PP-OCRv6_medium_rec_onnx`) evaluated over the deskewed comb strip with red-line removal.
- **Verification & Review**:
  - The reader extracts CTC character sequence and enforces prefix `0801CA25` and valid roll-range constraints (`1000..1157`).
  - If length $\ne 12$, prefix invalid, or character confidence falls below routing threshold, the page returns `needs_review: true`.

### 6.2 Subject Code Reader (Batch-Level Consensus Field)
- **Evidence & Findings from Spikes 4 & 5**:
  - Spike 4 demonstrated that loose fallback ROIs captured multi-line header text (`(TOTAL 28/32 PAGES EXCLUSIVE OF COVER PAGE)`), breaking 1D sequence recognition.
  - Spike 5 (`experiments/spike5_subject_code/SPIKE5_REPORT.md`) tightened ROIs to isolate the subject line ($y \in [0.290, 0.345]$ on A, $y \in [0.265, 0.320]$ on B). Static fractional ROIs without page-anchor alignment suffered from vertical scan drift ($\pm 50-80$ px), producing 17.73% raw exact and 29.06% known-codes matched.
  - Furthermore, subject code is handwritten with substantial stroke variance and cursive abbreviation (e.g. `Computer Network` written instead of code `CT10715`).
  - **Decision**: Subject code is designated as a **batch-level field**. While each page records its individual raw and matched recognition, the definitive exam subject code is determined by **cohort-wide batch consensus voting** across all sheets in the bundle against `subject_codes.json`.
  - Field cropping is anchored relative to the detected enrolment comb band (sharing the identical vertical translation offset) with moderate margins to eliminate scan-drift clipping.

### 6.3 Total Marks Reader (Phase 2 & Legacy Flag)
- Currently, **no lightweight ONNX model exists** in the repository to read handwritten equation strings (e.g. `"23.5=28"`), circled half-marks, or cursive marks-in-words.
- **Phase 1 Strategy (Hot Path V2)**: Total marks recognition is gated behind a configuration flag: `ENABLE_TOTAL_MARKS_OCR` (default `false` on sub-second hot path).
  - When `true`: Uses the legacy path (`PaddleOCR` + Strategy B `fix_total_marks` + `combine_grand_total_and_words`) off the hot path as a background escalation.
  - When `false`: Returns `total_marks: null`, `status: "DEFERRED_PHASE2"`.
- **Phase 2 Strategy**: Train a compact CTC/CRNN model on the 291 annotated total marks crops + synthetic equation datasets to enable fast (< 100 ms) CPU inference.

## 7. Configuration Answers & Policy Matrix

1. **Question Marks Table in Production**: Gated behind `EXTRACT_QUESTION_MARKS=false` (default `false`). Setting to `true` extracts cell marks for audits when sub-second turnaround is not required.
2. **Subject Code Registry**: Master registry defined at `ocr_v2/configs/subject_codes.json`:
   ```json
   {"valid_codes": ["CT10718", "CT10715"], "allow_unregistered": false}
   ```
3. **Comb Cell Validation**: If the comb segmenter finds fewer or more than 12 cells, it returns `null` with `needs_review: true`.
4. **Latency Target**: Strict target of **< 2.0 s per page on CPU**.
5. **V2 Migration Toggle**: Controlled via environment variable `USE_OCR_V2=false` (default `false` until M6 milestone signoff).

## 10. Batch Consensus Architecture & Separation Rules

1. **Strict Layer Boundary**: Batch consensus is an **isolated post-processing layer** (`ocr_v2.consensus.batch_consensus`). It operates only on a collection of `PageResult` objects after single-page evaluation completes.
2. **Single-Page Immutability**: The batch consensus engine **never mutates or overwrites** single-page fields (`rollno`, `subject_code`, `total_marks`, `confidence`).
3. **Consensus Fields**: Modifies only `batch_assisted_value` and `batch_vote_evidence: {"consensus_code": "CT10715", "agreement_ratio": 0.96, "batch_size": 145}`.
4. **Disagreement Handling**: If a sheet differs from batch consensus, it is flagged with `needs_review: true` and `review_reasons: ["BATCH_CONSENSUS_DISAGREEMENT"]`.

## 11. Test, Evaluation & Gate Plan

### Evaluation Rules & Wilson 95% Confidence Intervals
- **Frozen-Test Inviolability**: The 30% frozen-test sets (**44 images in Benchmark A**, **44 images in Benchmark B**) must **never be inspected or used** to calibrate YAML coordinates, tweak regexes, or train ONNX weights.
- **Reporting Standard**: All field accuracy figures on frozen sets ($n=44$) must be accompanied by Wilson 95% score confidence intervals:
  $$\hat{p} \pm z \sqrt{\frac{\hat{p}(1-\hat{p})}{n} + \frac{z^2}{4n^2}} \Big/ \left(1 + \frac{z^2}{n}\right), \quad z=1.96$$
  *(For $n=44$, an observed accuracy of 95.0% has a Wilson 95% CI of $[83.5\%, 98.6\%]$. Single-sheet changes must be interpreted within this interval.)*
